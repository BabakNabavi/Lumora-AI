# AI Interior Studio

**An AI-powered interior design platform that transforms spaces through intelligent visual redesign.**

Upload a photograph of a room, choose a style, palette, lighting and mood, and get a redesigned
interior back — with a side-by-side comparison, a written design rationale, and a workspace to keep
it all in.

</div>

---

## Project overview

AI Interior Studio is a production-shaped full-stack application, not a demo. It has real
authentication, a credit ledger, an audited AI pipeline, an abstracted storage layer, an admin
panel and a design system built from scratch.

The two decisions that shape the codebase:

**The AI provider is an interface, not a dependency.** `AIProvider` defines one method. Three
implementations ship — an offline renderer, Replicate, and OpenAI — and switching between them is a
single environment variable. No route handler, service or component refers to a concrete provider.

**Nothing in the product is a placeholder.** Every image the app ships with is generated by a
perspective scene renderer in `scripts/lib/scene.mjs`, driven by the same design catalog the product
itself reads. The offline AI provider runs a real colour-grading pipeline over the uploaded
photograph rather than returning a stock image, so the whole product — comparison slider, gallery,
downloads, credit ledger — is genuinely exercised without an API key or a network connection.

## Features

### AI design workflow
- Five-step guided studio: upload → room → style → customise → generate
- Drag-and-drop upload with real progress, client and server validation, EXIF stripping
- 8 styles × 7 room types × 5 palettes × 4 lighting modes × 5 moods
- Paced generation screen that narrates the analysis stages and never reports "done" early
- Interactive before/after slider — pointer, touch and full keyboard support
- Dynamic AI design insights written from the actual brief, not boilerplate

### Product
- Guest demo: one full generation before any account exists
- Dashboard with overview stats, gallery, filters and pagination
- Per-design detail pages: comparison, brief, insights, download, share, duplicate, delete
- Unlisted share links (96-bit tokens, revocable, excluded from indexing)
- Favourites, renaming, regeneration with a fresh seed

### Accounts & economics
- Email + password with bcrypt, and Google OAuth 2.0 implemented directly against the endpoints
- Stateless JWT sessions (`jose`), HTTP-only cookies, edge-validated
- Password reset with hashed, single-use, expiring tokens
- Append-only credit ledger — every balance change is a transaction row
- Failed generations refund automatically; a provider outage costs the user nothing
- Free / Pro plans, wired for a payment provider without being coupled to one

### Admin
- Platform reports: users, designs, success rate, credits spent, average render time
- 14-day generation volume chart and style/room breakdowns (no charting library)
- User, design and generation browsers — every provider call with the exact prompt sent

### Engineering
- Type-safe end to end, `strict` TypeScript, zero `any` in application code
- Zod validation at every boundary, one error envelope for every failure path
- Server Components by default; client components only where interaction demands it
- Rate limiting on auth, upload and generation
- SEO: metadata, Open Graph, JSON-LD, sitemap, robots
- Accessibility: skip link, focus rings, ARIA slider, live regions, reduced-motion support
- 58-check end-to-end smoke suite

### Layering

Dependencies point one way: `app` → `server` → `lib` → `config`. A page never imports Prisma, a
service never imports React, and `lib` never imports from `server`.

### The design catalog

`src/config/catalog.json` is the single source of truth. It drives the studio UI, the asset
generator, the mock provider's grading coefficients, the prompt builder and the insight writer.
Adding a ninth style means editing one JSON file and re-running the asset generator.

### The AI service layer

```ts
interface AIProvider {
  readonly name: string
  readonly requiresApiKey: boolean
  isConfigured(): boolean
  generate(input: GenerationInput): Promise<GenerationResult>
}
```

`aiProvider()` resolves the configured implementation once per process. If a key-dependent provider
is selected but its credentials are missing, the offline renderer takes over instead of the request
failing — the substitution is logged and shown in the admin panel and in settings, so it is never
silent.

`runGeneration()` orchestrates one generation, and the ordering is deliberate:

1. **Charge the credit first** — the ledger transaction is the lock, so parallel requests cannot
   spend the same balance twice.
2. Create the design row as `PROCESSING` so it is visible while it runs.
3. Call the provider.
4. On any failure: mark `FAILED`, refund the credit, record the failed `Generation` row.

### Storage

```ts
interface StorageDriver {
  put(input): Promise<StoredObject>
  get(key): Promise<FetchedObject | null>
  delete(key): Promise<void>
  exists(key): Promise<boolean>
  url(key): string
}
```

`local` writes outside `public/` and serves through `/api/files/*`, so objects are not
world-readable by virtue of sitting in the static directory. `s3` works against AWS S3, Cloudflare
R2, MinIO and Backblaze B2. Keys are validated centrally — traversal is rejected as a 400 before any
driver sees it.

### Security posture

- Passwords: bcrypt, 12 rounds; verification does constant work whether or not the account exists
- Sessions: signed JWTs, HTTP-only, `SameSite=Lax`, `Secure` in production
- The token is a **routing hint only** — role, plan and credits are always re-read from the database
- OAuth `state` is a nonce round-tripped through a cookie; the post-login redirect is same-origin only
- Uploads: magic-byte sniffing, decode verification, dimension bounds, full re-encode (strips EXIF/GPS)
- API keys are read only in `server/` and `lib/` modules marked `server-only`
- Login and password reset give identical responses for unknown accounts

## Environment variables

Copy `.env.example` to `.env`. Only the first three are required.

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | ✅ | Any PostgreSQL 14+. `npm run db:server` provides one. Append `?pgbouncer=true` behind any connection pooler. |
| `AUTH_SECRET` | ✅ | 32+ random chars. `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` |
| `NEXT_PUBLIC_APP_URL` | ✅ | `http://localhost:3000` in development |
| `AI_PROVIDER` | – | `mock` (default) · `replicate` · `openai` |
| `REPLICATE_API_TOKEN` / `REPLICATE_MODEL_VERSION` | – | Required when `AI_PROVIDER=replicate` |
| `OPENAI_API_KEY` | – | Required when `AI_PROVIDER=openai` |
| `STORAGE_DRIVER` | – | `local` (default) · `s3` |
| `S3_BUCKET` / `S3_REGION` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | – | Required when `STORAGE_DRIVER=s3` |
| `S3_ENDPOINT` / `S3_PUBLIC_URL` | – | For R2 / MinIO / B2 and CDN origins |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | – | The Google button hides itself when unset |
| `BILLING_PROVIDER` | – | `none` (default) · `stripe` |

The environment is parsed and validated once through Zod (`src/lib/env.ts`); a misconfiguration
fails loudly at startup with a readable message rather than as an undefined at runtime.

## Database setup

### Option A — zero install (recommended for a first run)

```bash
npm run db:server             # terminal 1 — embedded PostgreSQL on :5433
npm run db:push && npm run db:seed   # terminal 2
```

`db:server` starts PGlite behind a real PostgreSQL wire-protocol socket. Prisma, `psql` and anything
else connect to it exactly as they would to a normal server — the schema stays `provider =
"postgresql"` and nothing about the application changes. Data persists in `.pgdata/`.

It multiplexes every client connection onto one PGlite instance, so they share a prepared-statement
namespace. The supplied `DATABASE_URL` therefore carries `pgbouncer=true`, which tells Prisma not to
use prepared statements — the same flag you would set behind PgBouncer, the Supabase pooler, a Neon
pooled endpoint or RDS Proxy. Drop it when connecting straight to a dedicated instance.

Stop it with Ctrl-C. It is a WASM PostgreSQL writing to `.pgdata/`, so force-killing the process
(`taskkill /F`, `kill -9`) can corrupt that directory the same way it would corrupt a real cluster.
If it ever refuses to start, `rm -rf .pgdata` and re-run `db:push` + `db:seed` — nothing of value
lives there.

### Option B — your own PostgreSQL

Point `DATABASE_URL` at any PostgreSQL 14+ instance, then:

```bash
npm run db:push               # or: npm run db:migrate
npm run db:seed
```

The seed creates two accounts and twelve finished designs, deriving a matching "before" photograph
from each generated render so the comparison slider has real paired images:

| | Email | Password |
|---|---|---|
| Member | `demo@interiorstudio.app` | `Studio2026` |
| Admin | `admin@interiorstudio.app` | `Studio2026` |

### Verification

```bash
npm run dev                   # terminal 1
npm run test:smoke            # terminal 2 — defaults to :3000
```

The smoke suite walks the product the way a user does: browses the marketing pages, runs a guest
generation, exhausts the demo allowance, signs in, uploads, generates, favourites, shares, revokes,
downloads, duplicates, renames and deletes — then checks the authorisation boundaries (signed-out redirects,
cross-account access, non-admin bounce, path traversal) and the admin surface.

`npm run test:browser` covers what HTTP cannot. It drives the locally installed Chrome through
puppeteer-core (nothing is downloaded) across mobile / tablet / desktop viewports and asserts: no
console errors or warnings, no page errors, no failed requests, no broken images, no horizontal
overflow, and that the before/after slider responds to the keyboard. Screenshots land in
`scripts/audit/`.

## Production build

```bash
npm run build
npm run start
```

The build runs the asset generator first, so a fresh clone or a CI container produces its own
artwork — nothing binary is committed.

### Deploying

Set the environment variables above, point `DATABASE_URL` at a managed PostgreSQL, and set
`STORAGE_DRIVER=s3` with a bucket. Serverless platforms have ephemeral filesystems, so the local
storage driver only suits a host with a persistent volume.

The generation route declares `maxDuration = 300`; hosted image models routinely take longer than a
default serverless timeout allows.

> **Note on fonts.** The interface uses a system font stack (`ui-serif`/`ui-sans-serif`), so it
> ships no webfonts and has no render-blocking font request. The Open Graph image is rasterised at
> build time and expects a serif face to be installed — on a bare Linux container, install
> `fonts-liberation` or swap `og.png` for a static file.

## AI provider setup

The application works fully with no provider configured. To route generations to a hosted model:

### Replicate

```env
AI_PROVIDER="replicate"
REPLICATE_API_TOKEN="r8_..."
REPLICATE_MODEL_VERSION="<version hash of an SDXL img2img / interior model>"
```

The photograph is sent as a data URI, so no public URL has to exist first. `prompt_strength` is set
to 0.72 — high enough to restyle, low enough to keep the room's geometry.

### OpenAI

```env
AI_PROVIDER="openai"
OPENAI_API_KEY="sk-..."
OPENAI_IMAGE_MODEL="gpt-image-1"
OPENAI_VISION_MODEL="gpt-4.1-mini"
```

The image edit produces the render, then a vision pass writes the design commentary from the
**actual result** rather than from the brief. If that second call fails, the deterministic insight
writer covers the gap — a partial outage degrades copy quality instead of failing the generation.

### Adding a provider

1. Implement `AIProvider` in `src/lib/ai/providers/`.
2. Add one line to the registry in `src/lib/ai/index.ts`.
3. Add the name to the `AI_PROVIDER` enum in `src/lib/env.ts`.

No frontend change is required — the studio, the result page and the dashboard consume
`GenerationResult`, not a provider.

### The offline renderer

`MockAIProvider` is a mock in that no model is called, but it is not a stub. It composes the style,
palette, lighting and mood coefficients from the catalog into a real `sharp` pipeline — hue,
saturation, exposure, mid-grey-pivoted contrast, gamma, a multiply tint, a directional light wash
and a vignette — so every combination produces a visibly different, plausible result. Run
`npm run preview:grades` to see six briefs applied to one photograph.
